# Sync the Faustine adapter

The registry `faustine/registry.ts` (or `src/faustine/registry.ts`) is the
list of server functions this app's Faustine Web Agent may call: one line per
operation, a name Faustine knows and an import of the real function. It was
generated by `/enable-faustine-adapter`; the app kept changing since. Faustine
reads the registry at every push and shows what is missing on the Web Agent's
Overview (*To review*). Your job is to close that gap deliberately: audit,
plan, apply — one change at a time, no resets, nothing exposed the user did
not see.

Everything mechanical is the generator's: `npx faustine-next sync`. It keeps
the registry's own selection (a line the developer removed stays removed),
adds the operations that are new since the last report, and tells Faustine the
new hash. You decide, with the user, what goes in.

## Before editing

1. **Confirm the adapter is installed**: the registry file exists and
   `@faustine-ai/next` is in `package.json`. If not, this is an install — stop
   and use `/enable-faustine-adapter` instead.
2. **Confirm the token**: a second run needs no setup code; the adapter token
   is stored on this machine, scoped to this Web Agent. If `sync` answers
   *no adapter token*, ask the user for a new setup code from the portal
   (Web Agent → Overview → the adapter card, or Settings → Faustine adapter)
   and run `npx faustine-next init --setup <code>` — same files, same result.
3. **Read the registry** and the git diff of the app since the registry last
   changed (`git log -1 -- faustine/registry.ts`, then the Server Action and
   data-layer files that changed after it). Know what the user added, renamed
   or removed before the generator tells you.

## Audit

```bash
npx faustine-next sync --dry-run      # what would change, and why each operation is left out
npx faustine-next sync --check        # exit 1 when the registry would change (the CI gate)
```

Read the plan as three lists and show them to the user:

- **New operations** Faustine named since the last sync (added Server Actions or
  data functions). Each needs a decision: expose, or leave private.
- **Removed from the registry** — lines the developer deleted on purpose. The
  generator keeps them out; never add them back.
- **Left out** — route handlers (already reachable), inline reads (not bindable;
  the surface map names the function to extract), symbols that are not
  identifiers.

If the portal reports a **broken binding** (a function renamed or deleted
while the registry still imports it), that is the first thing to fix: the
app's build fails on it. A rename keeps the operation name — only the import
changes; the generator rewrites that line from the surface map.

## Plan

One change per operation, in the user's words: *expose `invoices.send`
(new Server Action in `app/invoices/actions.ts`)*, *keep `deals.deleteDeal`
private*, *fix `deals.getDeal` — the function moved to `lib/data/deals.ts`*.
Ask before exposing anything that writes or deletes; never widen the list
"to be safe". Noninteractive (no one to answer): stop and report the lists
instead of guessing.

## Apply

```bash
npx faustine-next sync                                   # the agreed selection: new ones in, removed stay out
npx faustine-next sync --operations deals.createDeal,…   # only when the user wants an explicit list
```

Without a terminal add `--yes`. The generator rewrites the registry, leaves the route
handler and the `AGENTS.md` block as they are unless they drifted, and reports
the registry hash to Faustine (*Adapter generated, waiting for a push*).

Never edit the registry by hand to add an operation, never rename an
operation: the names are what the agent knows.

## Verify

1. `npm run build` passes (a bad binding fails here, by design).
2. Start the app; `npx faustine-next doctor` compares this checkout, the
   running app and Faustine: it says where the adapter stands and what is
   still missing. Expect *waiting for a push* until you commit.
3. Commit the registry with the code change that caused the sync (`Sync the
   Faustine adapter: invoices.send`), push, deploy with the app's own
   pipeline. The portal flips to *In the repo* on the push (seconds, no
   analysis), and the *To review* item closes; *Deployed* follows the first
   manifest fetch of the new build.
4. If the new operation should be callable, the user publishes the Web Agent
   version that includes its method — the portal's Overview says so.

## Guardrails

- Keep the developer's removals: a line deleted from the registry is a
  decision, not drift.
- Never expose an operation the user did not see in the dry-run list.
- Never commit or print a setup code or adapter token (`fns_…`, `fna_…`).
- `sync --check` in CI is a gate on the registry file only; it never writes.
- A failing `sync --check` after someone else's push means their Server Action
  is not bound yet: run this skill on their branch, do not force the gate off.
